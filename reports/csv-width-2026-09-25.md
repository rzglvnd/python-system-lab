# CSV memory versus individual record width

Measured on 2026-09-25. With 1,000 records and a fixed three-column schema,
streaming peak traced allocations increased from 47,411 bytes at a 16-character note
to 659,665 bytes at a 65,536-character note. Eager loading increased from 375,993 to
66,196,346 bytes. The result shows that streaming avoids retaining all rows, but
its measured parsing-and-aggregation peak still increases with field width.

These are Python allocation measurements for this input and consumer, not total
process RAM, throughput, or a universal memory bound.

## Reproduce

```sh
python benchmark_csv.py run --sizes 1000 --widths 16 1024 16384 65536 --repetitions 3 --output reports/csv-width-local.json
```

The command generates deterministic temporary datasets, launches a fresh worker
per mode and repetition, validates counts and checksums, and removes the input
files afterward. The preserved [raw results](csv-width-2026-09-25.json) contain
all 24 trials, file hashes, worker PIDs, and environment metadata.

## Method and environment

- CPython 3.13.7, 64-bit, Windows 11 build 26200, Intel Core i7-12700H.
- One thousand records, three columns, UTF-8, LF record separators.
- The `note` field is a deterministic repetition/truncation of
  `alpha, "beta"\ncafé`. All widths include quoting and embedded newlines.
  The 16-character prefix ends before `é`; the larger widths include non-ASCII
  text. Character composition and Python's string representation can therefore
  also influence the smallest-to-larger comparison.
- Widths are 16, 1,024, 16,384, and 65,536 Unicode code points, as counted by
  Python's `len(str)`, not UTF-8 bytes. The JSON `note_width` field uses this unit.
  Generated files were
  35,015; 1,211,015; 19,131,015; and 76,475,015 bytes respectively.
- `tracemalloc` starts immediately before opening the input in a fresh worker.
  Peak includes opening, decoding, parsing, dictionary creation, aggregation,
  and closure; imports and dataset generation are excluded.
- Streaming passes the parser directly to the checksum aggregator. Eager mode
  retains `list(read_records(stream))` before aggregation. Both perform the same
  work and produce the same checksum.
- Three repetitions ran for each mode and width, with mode order alternating.

## Results

The minimum, median, and maximum were identical for each pair in this run. Raw
trials are retained so this can be checked rather than inferred from rounding.

| Note width (code points) | Input bytes | Streaming peak bytes | Eager peak bytes | Streaming KiB | Eager MiB |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 16 | 35,015 | 47,411 | 375,993 | 46.3 | 0.36 |
| 1,024 | 1,211,015 | 66,223 | 1,403,984 | 64.7 | 1.34 |
| 16,384 | 19,131,015 | 181,794 | 16,812,236 | 177.5 | 16.03 |
| 65,536 | 76,475,015 | 659,665 | 66,196,346 | 644.2 | 63.13 |

All 24 trials matched the expected record count and field-order-sensitive SHA-256
checksum. At the largest tested width, eager traced allocations were about 100.3
times streaming's peak. Streaming's peak increased with the current record's
size; it did not remain nearly flat as it did when row width was fixed and row count
increased.

## Interpretation and limits

The generator no longer retains all records, but a CSV parser must materialize a
logical record before yielding it. A single multiline field therefore creates a
real lower bound on transient memory. Eager mode adds retention of every parsed
dictionary, so its peak is affected by both record width and row count.

The measured region also serializes each record to JSON, encodes it as UTF-8,
and appends a newline before hashing. Those temporary allocations grow with the
record too. A peak alone cannot attribute the increase to parser buffers versus
aggregation; allocation snapshots or separate measurements would be needed.

The metric is `tracemalloc`'s traced Python allocations. It does not capture all
native allocations or report RSS, working set, file-system cache, or total
process memory. No timing or throughput claim is made. The repeated payload,
fixed row count, four widths, and one Python version limit generalization. Widths
were kept below the default CSV field-size limit; this report does not test limit
failures or large-record recovery.

This evidence supports a practical rule: streaming controls retention across rows,
but it cannot make an individual record free. A production ingestion path should
bound field sizes, choose an explicit policy for oversized records, and monitor
the consumer's own retention. The next experiment should test the parser's field
size limit and the resulting failure contract.

Reference: [Python `tracemalloc` documentation](https://docs.python.org/3/library/tracemalloc.html).
